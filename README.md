# 로컬 에이전트 파일럿 — 기술 노트

## 1. 왜 만들었나
신용협동조합 창구에서 일할 때, 반복되는 규정 확인과 상담 메모 정리에 AI를 쓰고 싶었지만 보안 규정상 클라우드 AI는 쓸 수 없었다. USB 반입도 건별 허가 대상이고 고객정보는 어떤 형태로도 외부로 나갈 수 없는 환경이다. 신협은 그 제약을 직접 겪은 자리일 뿐, 제약 자체는 민감정보를 다루는 모든 현장에 있다. 그래서 개인 PC 안에서만 도는 로컬 에이전트를 직접 만들어, 그런 환경에서도 성립하는 형태가 있는지를 검증했다. 완성 기준은 데모가 아니라, 다음 현장에 가져가 바로 실행할 수 있는 도구다.

## 2. 설계 원칙
- **로컬 완결**: 추론·색인·저장이 전부 한 대의 PC 안에서 끝난다. 외부 API 호출이 구조적으로 없다 (모델 서버는 localhost 전용, 계정 가입 자체가 필요 없는 실행 방식을 택했다).
- **마스킹 우선**: 주민등록번호·계좌번호·전화번호·카드번호·이메일·성명 패턴을 탐지해, 모델에 입력되기 전에 가린다. 원본 데이터는 기기 밖으로 나가지 않고, 모델이 보는 것도 마스킹된 텍스트뿐이다.
- **근거 기반 답변**: 업무 문서 폴더를 색인해 두고, 답변은 색인된 문서 안에서만 생성한다. 근거가 없으면 "문서에서 확인되지 않습니다"라고 답하게 했다 (창구 업무에서 지어낸 답은 사고로 이어지기 때문).
- **폐쇄망 반입 가능성**: 추가 클라우드 계정이나 외부 패키지 없이, Python 표준 라이브러리만으로 동작하게 만들었다.

## 3. 환경과 모델 선택
- PC: Intel i7-8700 / RAM 16GB / NVIDIA RTX 2060 (VRAM 6GB) / Windows 64비트. NPU가 없는 구형 PC라는 제약이 오히려 설계 기준이 됐다 — 화려한 모델이 아니라 이 사양에서 실제로 도는 모델을 골라야 했다.
- 실행: Ollama 0.40.14 로컬 서버 (localhost:11434 전용).
- 모델: EXAONE 3.5 (LG AI연구원, 한국어 특화 오픈 모델). 7.8B(Q4)를 기본으로, 2.4B를 속도 대안으로 실측 비교했다. 문서 검색과 마스킹은 모델이 아니라 색인·정규식이 담당해 두 모델의 적중이 같았고, 차이는 생성 속도와 답변 품질뿐이었다. 그래서 용도를 나눴다 — 근거 답변이 필요한 질의는 7.8B, 빠른 메모 요약·분류는 2.4B.
- 문서 검색: 외부 라이브러리 없는 문자 n-gram 코사인 색인 (문서 단락 단위).
- 설치 중 실제로 겪은 제약: 이 PC의 C드라이브 여유가 약 3.6GB뿐이라 4.8GB 모델을 받을 수 없어, 모델 저장소를 여유 있는 드라이브로 분리했다. 현장 PC의 디스크 사정까지가 배포 조건이라는 걸 확인한 셈이다.

## 4. 만든 것
- `agent.py` — 대화형 에이전트. 문서 질의응답 모드와 상담 메모 마스킹+요약 모드. 질문 자체에 개인정보가 섞여 있어도 모델에 보내기 전에 마스킹한다.
- `docs/` — 데모용 가상 업무 문서 2종 (실제 금융기관 내부자료가 아닌 창작 샘플).
- `bench.py` — 실측 스크립트. 응답 속도, 문서 검색 적중, 마스킹 탐지를 자동으로 재서 results.json으로 남긴다.
- `measure.py` — GPU 적재 상태와 속도 관계를 따로 확인한 진단 스크립트.

## 5. 실측 결과 (bench.py 측정, 2026-11-04, RTX 2060 6GB)
- **응답 속도 (400토큰 생성 기준)**
  - EXAONE 3.5 7.8B: **33.6 tokens/s** (튜닝 후, 아래 참조)
  - EXAONE 3.5 2.4B: **108.5 tokens/s**
  - 튜닝 과정: 7.8B 기본 설정에서는 8.5~9.8 tokens/s에 그쳤다. 원인을 확인하니 모델 5.49GB 중 4.16GB만 VRAM에 올라가고 나머지가 CPU로 내려가 있었다. 전 층을 GPU에 올리도록 지정하자 VRAM 적재가 5.05GB로 늘고 속도가 29.1 tokens/s로 뛰었으며, 최종 설정(컨텍스트 4096 + 전층 GPU)에서는 33.6 tokens/s를 기록했다. 6GB VRAM에서 7.8B를 돌릴 때는 이 적재 설정이 성능을 좌우했다.
- **문서 검색 적중: 5/5** — 샘플 질문 5개 전부 의도한 문서를 1순위로 찾았다.
- **마스킹 탐지: 10/10** — 샘플 문장의 민감 패턴 10건을 전부 탐지했다. 단, 첫 측정에서 카드번호가 계좌번호 패턴에 먼저 걸려 뒷자리 4자리가 남는 부분 노출을 발견했다. 패턴 적용 순서를 카드번호 우선으로 고친 뒤 전문이 가려지는 것을 재측정으로 확인했다. 탐지 개수만 세는 지표였다면 놓쳤을 문제라, 마스킹 결과 문자열까지 검사하는 방식으로 측정했다.
- **종단 동작 확인**: "보이스피싱이 의심되는 이체 요청을 받으면 어떻게 해야 하나요?"에 문서 기반 절차 답변 + 근거 문서 표기, "고액 현금거래는 얼마부터 보고 대상인가요?"에 "1천만원 이상"이라는 문서 수치 그대로 답변하는 것을 확인했다. 상담 메모 마스킹+요약도 마스킹 기호를 유지한 채 요약됐다.
- **오프라인 동작**: 코드의 네트워크 호출 지점은 localhost 한 곳뿐이며 외부로 나가는 연결이 없다. 네트워크를 끊은 상태의 실행 캡처는 별도 증거로 첨부한다.
- **엣지케이스 검증 (추가 실측)**: 문서에 없는 질문(환율)에는 "문서에서 확인되지 않습니다"로 답해 환각 방지가 동작했다. 검색 임계값은 감으로 정하지 않고 실측으로 정했다 — 문서 내 질문의 최저 점수 0.243, 문서 밖 질문의 최고 점수 0.058 사이인 0.10으로 설정했다. 마스킹은 별도 엣지 세트로 다시 쟀다. 첫 측정에서 ① 유선전화가 계좌번호로 오분류 ② 대표번호(1588-) 미탐 ③ 주민등록번호 공백형·무구분 13자리 미탐 ④ 이름이 두 명이면 두 번째 미탐 ⑤ 휴대폰·계좌 공백 구분형 미탐이 나왔다. 패턴을 확장·교정한 뒤 같은 세트로 재측정해 전부 해소됐고, 기존 벤치(탐지 10/10, 검색 5/5, 34.3 tokens/s)도 회귀 없이 유지됐다. 또 마스킹 도구가 탐지 내역을 출력할 때 원본 값을 그대로 찍던 것을 종류·건수만 남기도록 고쳤다 — 가리는 도구가 로그에 원본을 남기면 설계가 무너지기 때문이다.

## 6. 한계와 다음
- 내용이 빈약한 입력(제목만 있는 메모)에서는 모델이 없는 내용을 지어내 요약한 사례를 1건 확인했다. 근거 문서 기반 질의와 달리 자유 요약은 환각을 막을 장치가 약하다 — 실무 적용 시 입력 검증과 "근거 없으면 비워 두기" 규칙이 필요하다.
- 검색 색인이 단순해 문서가 수백 건으로 늘면 임베딩 기반으로 바꿔야 한다.
- 마스킹은 정규식 패턴 기반이라, 형식이 다른 번호는 놓칠 수 있다. 특히 "김민수 고객이…"처럼 라벨 없이 문장 안에 들어간 이름은 패턴으로 잡지 못해, 질문에 섞인 이름이 답변에 그대로 나타난 사례를 확인했다. 이름 탐지는 형태만으로는 한계가 있어, 실무 적용 시 형태소 분석이나 개체명 인식이 필요한 지점이다.
- 그럼에도 "민감한 정보를 다루는 현장에서는 로컬이 유일한 형태"라는 판단과, 구형 PC 사양에 맞춰 실제로 돌려 본 경험이 이 파일럿의 수확이다.

## 7. 제품 형태(UI)로 확장 (2026-11-06)
- 완성 기준을 "동작하는 코드"에서 "현장에서 바로 실행해 쓰는 도구"로 올렸다. 신협은 문제를 본 자리일 뿐이고, 도구의 목적지는 같은 제약을 가진 모든 현장이기 때문이다.
- `app.py` + `ui.html`: Python 표준 라이브러리 http.server 기반의 로컬 웹 UI. 서버도 127.0.0.1에만 바인딩해 외부 수신 자체가 없다. 실행.bat 더블클릭 → 엔진(Ollama) 자동 기동 확인 → 브라우저 화면 자동 열림.
- 화면 구성은 현장 직원 기준으로 설계했다: 엔진·모델·문서 상태를 항상 보이는 상태 카드, 근거 문서와 원문을 펼쳐 확인할 수 있는 답변 카드, 개인정보를 가린 뒤에만 요약하는 메모 화면, 문서 추가·모델 전환·글자 크기 조절. 오류도 개발자 문구가 아니라 "무엇을 하면 되는지"로 안내한다.
- API 스모크 테스트로 전 경로 검증: 상태·문서 목록·마스킹(성명·전화·계좌·주민번호 동시 탐지)·문서 밖 질문의 근거 없음 응답·엔진 미실행 시 503 안내까지 확인. 실제 모델 연결 테스트는 대상 PC 배포 시 수행한다.

## 8. 디자인 개편과 기능 확장 (2026-11-06)
- 첫 UI가 "템플릿 같은 전형성"이라는 피드백을 받아, 디자인 스킬(tasteskill v2의 앱 화면 조사)의 방향 결정을 받아 개편했다. 채택 방향은 achromatic-ledger: 화면 장식(크롬)에는 색을 쓰지 않고, 색은 데이터 — 근거 표시와 가린 건수 — 에만 쓴다. 숫자는 타일 카드가 아니라 장부처럼 머릿선으로 나뉜 한 줄의 타입으로 놓는다. 그라데이션·그림자·둥근 배지 같은 전형 장치를 전부 걷어냈다.
- 이 제품만의 얼굴은 마스킹 그 자체로 잡았다. 가려진 자리는 검은 바에 종류만 흰 글자로 찍어 보여 주고(예: [주민등록번호]), 제품 마크도 가려진 줄 세 개를 쌓은 형태로 그렸다. 장부의 종이결에서 가져온 청회색 지면 위에 얹었다.
- 제약에 따른 조정: 웹폰트는 오프라인 원칙과 충돌해 쓰지 않고 시스템 폰트 스택(Pretendard 우선)으로 대체했다. 글자 크기는 보통·크게·더 크게 3단계로 직원이 고를 수 있다.
- 기능 확장: ① 답변이 실시간으로 흘러나오는 스트리밍 + 생성 속도(tok/s) 실측 표시 ② 문서 목록에서 단락 미리보기 ③ 최근 질문 기록(브라우저 저장, 클릭 재질문) ④ 질문용·요약용 모델 분리 설정 ⑤ 이번 실행에서 답한 질문·정리한 메모·가린 개인정보 건수 카운터(서버 실측) ⑥ 답변·결과 복사 버튼.
- 검증: 디자인 스킬 린트 0 FAIL·0 WARN, API 전 경로 스모크 테스트(스트리밍 메타·근거 없음 응답·모델 전환·문서 미리보기), 1440px 스크린샷으로 묻기·메모 두 화면 검수.
- 자원 관리: 엔진(Ollama)은 상시 실행하지 않는다. 실행.bat이 서버가 꺼져 있을 때만 직접 켜고(소유 플래그), 도구를 닫으면 함께 종료한다. 이미 켜져 있던 엔진은 건드리지 않는다. 모델은 keep_alive 2분으로 마지막 사용 후 메모리에서 내려간다. PC 배포 시 시작 프로그램의 Ollama 자동 시작도 함께 끈다.
